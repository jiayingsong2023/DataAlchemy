# DataAlchemy Agent Harness 待办清单

> 目标不是堆叠 Agent 功能，而是让模型在明确上下文、受控工具和真实环境中完成复杂任务，
> 并用独立证据证明完成、失败或需要人工决策。当前不引入第二个运行时；以 PostgreSQL
> `AgentRuntime`、Tool Gateway、MinIO 产物和发布治理为唯一权威路径。

## 完成标准

一个复杂任务只有同时具备下列证据才可称为完成：

```text
任务契约 → 受控执行 → 产物与状态 → 独立验证 → 可恢复/可回放决策
```

工具返回 `completed`、Kubernetes Job 成功或模型生成文本均不足以单独证明任务完成。

## P0：可验证执行核心

### 1. 任务契约与统一运行编号

- [ ] 每个任务在执行前持久化 `TaskSpec`：目标、成功谓词、允许工具与数据范围、tenant、
  预算、超时、审批点、幂等键和计划版本。
- [ ] 由 API 创建真正的多步骤计划；`Plan → Act → Observe → Replan` 的 replan 必须能
  产生受审计的新计划，不能只记录同名事件。
- [ ] 为一次复杂任务分配唯一 `run_id`，关联 PostgreSQL 任务/事件、Spark Job、训练 Job、
  原始数据、评测报告、adapter 与发布记录。

### 2. 工具契约与受控环境

- [ ] 每个工具声明输入 schema、最小权限、读写范围、速率/成本/重试预算、可撤销性、
  预期产物和成功/失败类型；禁止只有模糊 `status: completed` 的副作用工具。
- [ ] 将 Git、Jira、Confluence、PDF/DOCX、网页/API 等外部输入统一为受限 Connector：
  显式身份、源 ACL、落地前校验、版本/删除同步和审计。
- [ ] 长时或有副作用的工具在受限 Worker/Job 中运行；运行时只持有任务句柄和最小能力，
  不能因工具失败丢失 tenant、审批或恢复语义。

### 3. 独立验证、恢复与证据包

- [ ] 每个关键阶段由独立 verifier 验证，而非相信执行器自报成功：清洗质量与脱敏、
  文档/chunk/ACL 可检索性、记忆范围、LoRA 固定评测、发布 guardrail 与回滚目标。
- [ ] 将输入版本、输出计数、产物 URI/hash、日志链接、verifier 结论、失败原因和人工决定
  写入不可变 run manifest；任务可从最近已验证 checkpoint 恢复。
- [ ] 将现有 Spark/Operator 与旧 full-cycle 路径接入该 run，而不是由 Kubernetes 注解绕过
  `AgentRuntime` 和任务事件。

### P0 退出门禁

- [ ] 一个故意失败的多步骤任务可显示失败阶段、保留已验证产物、拒绝未验证后续步骤，并从
  checkpoint 恢复。
- [ ] 一个成功任务可从 `run_id` 重放所有输入、工具调用、产物、验证和审批结论。

## P1：Agent 可理解性与完整产品闭环

- [ ] **Context / Skills 包**：按任务提供版本化目标、数据源契约、工具使用规则、已知限制、
  成功样例与失败处置；运行时只装载当前任务所需上下文。
- [ ] **产品完整闭环展示**：在 WebUI 用一个 `run_id` 展示原始数据、Spark rough clean、
  refine/synthesis、文档/chunk、RAG 验证、反馈审核、记忆、训练候选、LoRA、评测和发布门禁；
  每一步展示状态、计数、证据、日志、审批和失败原因。
- [ ] **受控 PDF/DOCX 试点路径**：沿 Connector → Spark → verifier → PostgreSQL 的完整路径；
  不绕过接入、脱敏、tenant 和审计门禁直接写入检索表。
- [ ] **外部信息任务样例**：至少用一个真实只读业务任务验证自动抓取、来源比较、人工审批和
  报告产出；不以单文档检索 smoke test 代替。

## P2：上下文、记忆与冲突治理

- [ ] **Memory distillation**：在会话结束或达到轮数阈值时提炼摘要、偏好、待办和程序性知识；
  每条记忆带来源事件、tenant、置信度、有效期和写入策略。
- [ ] **分级写入与授权**：低风险个人记忆可自动生效；跨用户、组织规则和高风险内容进入指定
  管理员审批；密钥、权限、财务、人事内容默认拒绝。收紧当前任何同 tenant 用户可审批候选的边界。
- [ ] **冲突处置与用户控制**：对文档、连接器版本和记忆保留来源、时间、ACL 与置信度；按明确
  权威规则自动 supersede，否则展示冲突证据并进入人工裁决。用户可查看、修订、删除、禁用自动
  记忆和设置保留期。

## P3：评测、学习与安全发布

- [ ] **轨迹评测集**：覆盖工具选择、ACL 越权拒绝、输入污染、冲突、失败恢复、人工审批和
  证据完整性；评测断言过程及副作用，而不只比较最终回答。
- [ ] **在线质量闭环**：按 `run_id` 收集可审核反馈、失败分类、成本/延迟与 verifier 失败率；
  仅将满足 tenant 许可和审核策略的数据加入训练候选。
- [ ] **LoRA 发布门禁**：训练快照、基线对比、固定评测、shadow、canary 和回滚均关联同一
  证据包；训练入口自身强制前置条件，不能靠上游约定。

## P4：试点运维与正式发布

- [ ] **隔离测试环境重置**：提供当前 Helm 路径的显式确认脚本，可选择清理专用测试
  PostgreSQL、MinIO 前缀、Redis 测试键和本地 k3d；默认不得触碰共享或生产资源。
- [ ] **生产 OIDC 联调**：在目标 IdP、真实 tenant/role claim 与审计留存策略下完成验收。
- [ ] **GA-01 外部试点**：两支独立真实团队连续四周使用，完成周度审计、价值回顾和安全签署。

## 排序原则

- 先让系统可验证地完成一个复杂任务，再增加新 Connector、记忆自动化、LoRA 或多 Agent。
- 不以模拟成功、模型自评、单元测试或 Job 结束代替独立验证。
- 未具备 P0 证据包时，项目只能称为内部发布候选；单文档入库仅是检索 smoke test。
