# Phase 4：企业治理与可控学习实施计划

## 定位与前置条件

Phase 3 已通过模拟试点预演，当前状态是**发布候选**，不是正式生产发布。本阶段可以在
没有两支真实团队的情况下完成工程门禁；真实双团队连续四周试点改为 `GA-01`，是
Phase 4 之后的正式生产发布条件，而非本地可关闭的开发任务。

Phase 4 分支应在当前堆叠链未合并时从 `feat/phase-3-tooling-pilot` 的最终提交创建：
`feat/phase-4-governance-learning`。不得从缺少 Phase 0--3 安全、运行时和记忆治理
成果的 `main` 创建。

不在本阶段引入图数据库、第二个连接器或多智能体；也不允许自动将未审核反馈用于训练。

## P4-A：企业身份、策略与统一审计

目标：使每次受保护操作都具备可验证的身份、策略判定和审计链。

1. 实现通用 OIDC SSO（授权码 + PKCE）；生产环境禁用本地密码登录，开发环境保留受控
   本地账户路径。
2. 建立 `tenant → role → tool/document/memory/release` 策略映射；OIDC 的 subject、组和
   tenant 声明仅在服务器端验证与映射，不能由浏览器请求覆盖。
3. 建立 PostgreSQL 审计事件表和查询 API：记录认证、检索、记忆变更、工具调用、审批、
   外发、连接器运行和发布。审计记录包含 actor、tenant、动作、资源、结果、关联 ID、
   配置/版本摘要和脱敏元数据；不得存储 token、密码、原始提示词或工具秘密。
4. WebUI 增加管理员审计视图，按用户、任务、资源和时间筛选；普通用户仅可访问自身
   tenant 的允许记录。

验收：OIDC 声明伪造、跨 tenant、角色降级、拒绝工具调用与敏感字段审计均有正反测试；
可从一个任务追溯到身份、工具、记忆、来源和审批。

## P4-B：可恢复运营与 SLO 基线

目标：从“存在备份脚本”升级为可验证的恢复点与可观测运行服务。

1. 将 PostgreSQL dump、MinIO 原始对象/manifest、配置校验和发布指针组成带哈希的恢复包；
   Redis 明确为可丢弃 TTL 状态，不作为业务恢复源。
2. 在隔离命名空间恢复恢复包，验证 pgvector、文档 ACL、记忆、任务检查点、连接器游标、
   manifest/current 与增量重放；恢复过程不得连接或写入源环境。
3. 补齐 Prometheus 指标：任务和工具结果、队列/恢复、连接器、RLS 拒绝、审计写入、
   模型/工具延迟、GPU/存储及发布状态。
4. 用 Dogfooding 与压测记录 P50/P95、错误率、恢复时间、容量和成本基线；阈值先写入
   配置与报告，未有真实数据前不得凭空承诺生产 SLO。

验收：隔离恢复后无重复向量/外部副作用，且可继续增量同步；至少一次长稳预演无数据
损坏；指标与仪表盘可从 run/task/tenant 关联到审计事件。

## P4-C：记忆生命周期治理

目标：将 Phase 2 的可审批记忆扩展为可解释、可回放、可回滚的生命周期策略。

1. 为记忆增加策略版本、有效期、置信/冲突状态、保留原因、失效与归档操作记录。
2. 实现最小策略执行器：重复候选合并、同类冲突标记、基于策略的衰减/到期，以及已批准
   删除和保留例外；任何自动动作只产生候选或可撤销状态，不绕过审批。
3. 记录每次策略输入、决策、版本和前后状态；提供按 memory ID 的回放、撤销和管理员
   复核 API/UI。
4. 创建固定的冲突、过期、删除、跨租户与回滚评测集。

验收：同一策略与输入可重放得到相同决策；删除和过期后检索为零；回滚仅恢复授权的
历史版本，不恢复已撤销 ACL。

## P4-D：安全发布与可控学习

目标：让模型、Prompt、工具和数据集的每次改变都可比较、审批、灰度和回滚。

1. 创建统一 release manifest，关联代码提交、模型/Prompt/工具/索引/记忆策略版本、
   评测结果、审批人与可回滚目标。
2. 将 Phase 1--3 任务集、ACL/删除集、故障集和记忆治理集组成发布评测；候选必须相对
   当前版本满足预先记录的非退化门槛。
3. 建立影子和 tenant allow-list 灰度路径，记录线上候选结果但不影响正式回答；审批后
   才能晋级，错误率、延迟、安全拒绝或评测退化触发自动回滚。
4. 将反馈固定为“审核数据集候选”：只接受已审核、来源完整、已脱敏并按 tenant 许可的
   反馈；训练完成后必须在固定集与安全集比较，未提升的 LoRA 不得发布。

验收：在隔离环境连续完成两个发布周期（一次正常晋级、一次受控自动回滚）；未审核或
   无来源反馈无法进入训练数据集；任一发布可从 manifest 完整追溯并回到前一版本。

## P4-E：发布候选复核与真实试点准备

目标：将工程完成物转为可交给未来设计合作团队的发布候选，而不伪造客户验收。

1. 汇总 P4-A 至 P4-D 的测试、评测、恢复、长稳和两次发布周期证据，产出
   `../../release/PHASE4_RELEASE_CANDIDATE_REPORT.md`。
2. 完成内部 Dogfooding：两个隔离 tenant、脱敏真实资料、周度审计模板和安全联系人；
   该活动只作为内部 Alpha 证据。
3. 准备 `GA-01` 包：合作团队准入表、只读服务账户模板、任务集、数据处理边界、成功
   阈值、退出/停止条件和每周至少 10 个任务的审计表。

Phase 4 发布候选退出门禁：P4-A 至 P4-D 全绿、恢复演练与两个受控发布周期通过、内部
Dogfooding 无安全事件、`GA-01` 物料齐全。

## GA-01：正式生产发布门禁（外部，不可模拟）

两支独立真实团队各连续使用四周；每周审计至少 10 个任务的 ACL、来源、审批、恢复与
人工接管。任何跨 tenant、越权工具或记忆泄漏事件停止扩大使用并进入修复。只有满足
已签署的任务价值、稳定性与安全阈值后，才能标记正式生产发布。

## 实施顺序与验证

`P4-A → P4-B → P4-C → P4-D → P4-E → GA-01`。每一段单独提交并运行相应单元、
pgvector/RLS 集成、故障注入和评测；P4-E 汇总完整 CI、Helm 渲染、恢复与发布演练。
不要将 OIDC client secret、客户令牌、原始文档、审计原文或训练样本提交到仓库。
